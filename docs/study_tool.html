🎮 Pygame Squares Simulation

Interactive Learning Dashboard • Refactored Code Explorer

📋 Project Overview

A real-time 2D simulation built with Pygame where 20 squares move in a bounded window (800×600). Each square has unique behavior based on its size:

🏃 Smaller Squares

Flee from larger nearby squares within a 150px radius. They detect threats and move away.

🎯 Larger Squares

Chase smaller nearby squares within a 200px radius. They pursue prey actively.

🔄 Lifecycle

Each square has a 30-180 second lifespan. When it expires, a new random square replaces it to maintain stable population.

Core Simulation Rules

Every Frame:
1. Age each square and check for lifespan expiration
2. Find bigger/smaller squares nearby
3. Apply flee and chase steering behaviors
4. Update position based on velocity
5. Handle wall collisions and bouncing
6. Render to screen at 60 FPS

Technology Stack

Python 3.8+ Pygame 2.6.1 Dataclasses Type Hints

🎯 Key Features

Delta-Time Movement: Motion is scaled by frame time for consistent speed across all FPS values. Squares move pixels/second, not pixels/frame.
Speed Clamping: Each square has a max speed based on its size. Larger squares move slower to balance gameplay.
Vector Normalization: Flee and chase directions are normalized (unit vectors) before applying force strength for consistent behavior.
Emergent Behavior: Simple local rules produce complex global patterns. Swarms form, fleeing chains occur, predator-prey dynamics emerge.

🔗 Data Flow: One Frame

Trace how a single square is processed in one 60 FPS frame (Δt ≈ 16.67ms):

INPUT: squares list, screen bounds, delta_time ↓ FOR each square: AGE PHASE: age += delta_time IF age ≥ lifespan: → Replace with new random square, skip to next DETECTION PHASE: bigger_squares = find_bigger_nearby_squares(square, FLEE_RADIUS) smaller_squares = find_smaller_nearby_squares(square, CHASE_RADIUS) BEHAVIOR PHASE: apply_flee_behavior(square, bigger_squares, FLEE_STRENGTH * delta_time) → Accumulate flee forces → Normalize → Apply → Clamp speed apply_chase_behavior(square, smaller_squares, CHASE_STRENGTH * delta_time) → Accumulate chase forces → Normalize → Apply → Clamp speed MOVEMENT PHASE: x += vx * delta_time y += vy * delta_time COLLISION PHASE: IF x ≤ 0: x=0, vx *= -1 (bounce left wall) IF x+size ≥ width: x=width-size, vx *= -1 (bounce right wall) IF y ≤ 0: y=0, vy *= -1 (bounce top wall) IF y+size ≥ height: y=height-size, vy *= -1 (bounce bottom wall) OUTPUT: updated squares list

Understand how data moves through the system during simulation.

Square State Lifecycle

create_squares(20) → List of 20 fresh squares

Steering Force Pipeline

Flee Behavior: How Fear Becomes Motion

STEP 1: DETECT bigger_squares = find_bigger_nearby_squares(square, FLEE_RADIUS) → Returns list of all squares > current square within 150px STEP 2: ACCUMULATE VECTORS FOR each threat: dx = threat.x - square.x (vector toward threat) away_x -= dx / distance (reverse direction, normalize by distance) STEP 3: NORMALIZE length = √(away_x² + away_y²) away_x /= length (unit vector pointing away from all threats) away_y /= length STEP 4: APPLY FORCE vx += away_x * FLEE_STRENGTH * delta_time vy += away_y * FLEE_STRENGTH * delta_time STEP 5: CLAMP speed = √(vx² + vy²) IF speed > max_speed: scale = max_speed / speed vx *= scale, vy *= scale

Chase Behavior: How Hunger Becomes Motion

Same pipeline, but:

  • DETECT: find_smaller_nearby_squares(square, CHASE_RADIUS)
  • ACCUMULATE: toward_x += dx / distance (approach, not avoid)
  • APPLY: CHASE_STRENGTH instead of FLEE_STRENGTH
  • CLAMP: Same speed limiter

Time-Based Movement

Frame Timing (60 FPS): delta_time = clock.tick(60) / 1000.0 → On 60 FPS: delta_time ≈ 0.01667 seconds Velocity Integration: new_x = x + vx * delta_time new_y = y + vy * delta_time → If vx = 100 pixels/second and delta_time = 0.01667 → Movement = 100 * 0.01667 ≈ 1.667 pixels per frame Behavior Scaling: vx += away_x * FLEE_STRENGTH * delta_time → FLEE_STRENGTH = 80 pixels/second² → Force per frame = 80 * 0.01667 ≈ 1.33 pixels/second added

Spatial Queries

Neighbor Detection: filter_nearby_squares() uses O(n) linear scan per square. For 20 squares, this is negligible. At 60 FPS with 20 squares, each square checks ~160 neighbor pairs per second—well within real-time budget.
Distance Calculation: hypot(dx, dy) is accurate and fast. Used in both neighbor detection and vector normalization. No floating-point issues at these scales.

🔧 Refactoring Deep Dive

This version reflects a thoughtful refactoring focused on readability and maintainability for learners. Every change aims to make the code easier to understand and modify.

1. Module-Level Behavior Constants

❌ Before

def update_squares(...): for square in squares: # Magic numbers hidden! bigger = find_bigger( square, 150.0 ) apply_flee( square, bigger, 80.0 )

✅ After

FLEE_RADIUS = 150.0 FLEE_STRENGTH = 80.0 CHASE_RADIUS = 200.0 CHASE_STRENGTH = 60.0 def update_squares(...): for square in squares: bigger = find_bigger( square, FLEE_RADIUS ) apply_flee( square, bigger, FLEE_STRENGTH * dt )
Why: Tuning values are now visible at module level. Students can change one constant and immediately see the effect on simulation behavior. No hunting through function code. Concept: Configuration Over Magic Numbers

2. Unified Neighbor Filter Helper

❌ Before (Duplication)

def find_bigger(...): nearby = [] for other in squares: if other is square: continue if other.size <= square.size: continue if distance> radius: continue nearby.append(other) return nearby def find_smaller(...): nearby = [] for other in squares: if other is square: continue if other.size >= square.size: continue if distance > radius: continue nearby.append(other) return nearby

✅ After (DRY)

def filter_nearby_squares( square, squares, radius, size_compare ): nearby = [] for other in squares: if other is square: continue if not size_compare( other.size, square.size ): continue if distance > radius: continue nearby.append(other) return nearby def find_bigger(...): return filter_nearby_squares( square, squares, radius, lambda o, s: o > s )
Why: The filtering loop is identical in both functions—only the comparison predicate differs. Moving shared logic to one helper eliminates duplication (DRY principle). Easier to fix bugs: one fix applies to both functions. Easier to optimize: improve the loop once. Concept: DRY (Don't Repeat Yourself)

3. Centralized Speed Clamping

❌ Before (Repeated)

def apply_flee_behavior(...): # Compute forces... vx += away_x * force vy += away_y * force # Clamp speed speed = hypot(vx, vy) if speed > max_speed: scale = max_speed/speed vx *= scale vy *= scale def apply_chase_behavior(...): # Compute forces... vx += toward_x * force vy += toward_y * force # Clamp speed (repeated!) speed = hypot(vx, vy) if speed > max_speed: scale = max_speed/speed vx *= scale vy *= scale

✅ After (Helper)

def clamp_speed(square): """Enforce speed limit after steering forces are applied.""" speed = hypot( square.vx, square.vy ) if speed > square.max_speed: scale = ( square.max_speed / speed ) square.vx *= scale square.vy *= scale def apply_flee_behavior(...): # Compute forces... vx += away_x * force vy += away_y * force clamp_speed(square) def apply_chase_behavior(...): # Compute forces... vx += toward_x * force vy += toward_y * force clamp_speed(square)
Why: Speed clamping is an independent concern that appears after every force application. A helper makes the code more readable and maintainable. If clamping logic needs improvement, one change fixes both behaviors. Concept: Helper Functions Single Responsibility

4. Clear Variable Naming for Vector Math

❌ Before (Unclear)

x = 0.0 y = 0.0 for other in threats: dx = ... dy = ... distance = hypot(dx, dy) x -= dx / distance y -= dy / distance

✅ After (Descriptive)

away_x = 0.0 away_y = 0.0 for other in threats: dx = other.x - square.x dy = other.y - square.y distance = hypot(dx, dy) # Reverse direction away_x -= dx / distance away_y -= dy / distance # Later: normalize and apply away_x /= length away_y /= length
Why: The variable names now express intent: "away_x" clearly means "component of flee direction"; generic "x" and "y" obscure the meaning. For beginners learning vector math, clear names reduce cognitive load. Concept: Self-Documenting Code

5. Explicit Phase Comments in update_squares()

def update_squares(...): updated_squares = [] for square in squares: # Phase 1: Age and check for lifespan expiration. square.age += delta_time if square.age >= square.lifespan: updated_squares.append(create_random_square()) continue # Phase 2: Detect neighbors and apply steering behaviors. bigger_squares = find_bigger_nearby_squares(...) apply_flee_behavior(...) # Phase 3: Integrate position based on velocity. square.x += square.vx * delta_time square.y += square.vy * delta_time # Phase 4: Handle boundary collisions. if square.x <= 0: square.x=0 square.vx *=-1 # ... more boundary checks updated_squares.append(square) return updated_squares
Why: Comments mark distinct simulation phases. Students can trace one square through a complete frame without getting lost. Easier to understand game loop patterns. Easier to add features: "where do I add gravity? Phase 3." Concept: Game Loop Architecture

✨ Code Patterns & Best Practices

This project demonstrates several programming patterns that are useful for game development and simulation.

Good Patterns Used

1. Dataclass for Entity State

Using @dataclass for the Square ensures:

  • Type safety with annotations
  • Auto-generated __init__ method
  • Clear intent: "this is data"
  • Easy debugging with auto __repr__
@dataclass class Square: x: float y: float vx: float vy: float size: int max_speed: float age: float lifespan: float
2. Delta-Time for Frame-Rate Independence

Movement and forces are scaled by delta_time:

  • Behavior remains consistent at any FPS
  • Easy to slow-motion or speed-up simulation
  • Professional standard in game development
delta_time = clock.tick(FPS) / 1000.0 x += vx * delta_time vx += force * delta_time
3. Vector Normalization for Consistent Forces

Direction vectors are normalized (scaled to unit length) before applying force:

  • Force magnitude stays constant regardless of situation
  • No dependency on distance between entities
  • Predictable, balanced gameplay
# Combine directions away_x -= dx / distance away_y -= dy / distance # Normalize to unit vector length = hypot(away_x, away_y) away_x /= length away_y /= length # Apply constant force vx += away_x * FLEE_STRENGTH
4. Pure Functions for Math & Queries

Functions like distance_between(), compute_max_speed(), and filter_nearby_squares() are pure (no side effects):

  • Easy to test in isolation
  • No hidden state or surprises
  • Can call multiple times safely
5. Shared Factory for Initialization & Rebirth

Both initial creation and lifespan rebirth use the same create_random_square() function:

  • Consistency: new and respawned squares are identical
  • Easy maintenance: fix one, fix all
  • Encourages stable population
6. Type Hints Throughout

All functions use Python type hints:

  • Self-documenting: readers know what types are used
  • IDE support: autocomplete and type checking
  • Catches errors early
def filter_nearby_squares( square: Square, squares: List[Square], radius: float, size_compare, # Callable[[int, int], bool] ) -> List[Square]:

Patterns to Consider for Future Improvements

1. Type Hint for Predicates

The size_compare parameter in filter_nearby_squares() uses a lambda. Making the type explicit would improve clarity:

from typing import Callable def filter_nearby_squares( square: Square, squares: List[Square], radius: float, size_compare: Callable[[int, int], bool], ) -> List[Square]: # ...

This tells readers that size_compare is a function taking two ints and returning bool.

2. Collision Response with Elasticity

Currently, wall bounces reverse velocity (elastic collision, elasticity = 1.0). In future, make elasticity configurable:

ELASTICITY: float = 1.0 if square.x <= 0: square.x=0 square.vx *=-ELASTICITY # Easy to tune damping
3. Configurable Neighbor Radii per Square

Currently, FLEE_RADIUS and CHASE_RADIUS are global. Per-square radii could make behavior richer:

@dataclass class Square: # ... existing fields ... flee_radius: float = FLEE_RADIUS chase_radius: float = CHASE_RADIUS
4. Event System for Interactions

When a square catches another or dies, trigger events. This decouples behavior from physics:

class SquareEvent: CAUGHT = "caught" DIED = "died" def on_event(event_type, square, target=None): if event_type == SquareEvent.CAUGHT: # Score updates, sound effects, etc. pass
5. Spatial Partitioning for Scale

At 20 squares, O(n²) neighbor checks are fine. At 1000+ squares, use a grid or quadtree:

  • Divide screen into cells
  • Only check neighbors in adjacent cells
  • Reduces complexity from O(n²) to O(n)

Design Decisions & Rationale

Why Combine All Threats Before Normalizing?

Instead of normalizing each threat direction individually:

# DON'T: Normalize each threat separately for other in threats: away_x = -(other.x - square.x) / distance away_y = -(other.y - square.y) / distance away_x /= hypot(away_x, away_y) # Redouble work vx += away_x * force # DO: Accumulate, then normalize once (current approach) for other in threats: away_x -= dx / distance away_y -= dy / distance away_x /= length away_y /= length vx += away_x * force

Why: The second approach is more efficient (one normalization per square instead of per threat) and produces more balanced behavior (all threats equally influence the final direction).

📚 Suggested Reading & Resources

Game Programming Concepts

  • Game Loop: The main rhythm of any real-time game. Input → Update → Render → Repeat.
  • Delta Time: Frame-rate independent movement. Always multiply by Δt.
  • Vector Math: Position, velocity, and force are vectors. Learn dot/cross products for advanced behaviors.
  • Steering Behaviors: Classic AI patterns: seek, flee, pursuit, evasion, flocking.

Python & Software Engineering

  • Dataclasses: Modern Python way to define simple data containers.
  • Type Hints: Make code safer and more self-documenting.
  • DRY Principle: Don't repeat yourself. Extract common logic into helpers.
  • Pure Functions: Functions with no side effects are easier to test and reason about.

Debugging Practices
